# [0.4.1] - 2026-11-14

Campaigns, flows, the CMS home and the media library are reworked, and files that should never have a public
address get a store of their own: exports, form uploads and a private half of the library you can share with a
customer. Before upgrading a production install, add a second bucket with no public access and name it in
`PRIVATE_S3_BUCKET` (or `PRIVATE_STORAGE_DIR`) - the app now refuses to start without one. Two more changes reach
past the app itself: `myDownloads.productId` can be null on the storefront API, and the `download.accessed` webhook
can arrive with a null `ProductID` and a new `AssetID`.

### Added

- **Flows start from a recipe.** An empty flow offers a welcome series, abandoned cart, browse follow-up, back
  in stock and newsletter welcome, each with its trigger and steps already wired. Only the recipes whose trigger
  the install offers are shown, and the emails are left for you to pick.
- **A new step joins the flow by itself.** Clicking a step in the rail hangs it under the selected step, or at
  the end of the flow, and splices it in when something already followed. Deleting a step from the middle of a
  line joins the two ends. Dragging a step onto the canvas places it by hand.
- **The builder says what's wrong before a flow runs.** A step with no email picked, an empty SMS, a split or a
  segment step with no segment, a webhook with no URL, a trigger nothing follows and a flow that loops are marked
  on the canvas and listed under the Flow tab, and Activate waits until they're fixed. A step that isn't
  connected is flagged too, but doesn't hold the flow back.
- **Undo and redo, duplicate and tidy up.** The builder keeps the last fifty changes (Ctrl/⌘+Z and
  Ctrl/⌘+Shift+Z), duplicates the selected step (Ctrl/⌘+D), saves on Ctrl/⌘+S, and lines the steps up under the
  trigger with one button.
- **A send-email step shows the email it sends.** The step on the canvas carries the email's name, its settings
  show the subject and preheader, and Preview opens it the way the inbox would.

- **Where uploaded files are kept is a setting.** Settings, System, Media files holds four templates: how a
  library file is named inside its folder, and where product pictures, category covers and collection covers go
  under `catalog/`. They're written with placeholders, like `products/{sku}/{type}/{name}-{short_id}{ext}`,
  and each needs `{id}` or `{short_id}` so an address is never used twice. A template only applies to what is
  uploaded after it, plus library files that are moved or renamed.

- **Pictures can be edited in the media library.** A picked JPEG, PNG or WebP has an Edit picture button: crop
  freely or to a shape (square, 4:3, 3:2, 16:9, the original's), turn it, mirror it, and set brightness, contrast
  and saturation. The edit is saved as a new file beside the original, with the original's title, alt text and
  caption, and the original stays as it was.

- **The media library has a private half.** On an install with a private store (`PRIVATE_S3_BUCKET` or
  `PRIVATE_STORAGE_DIR`), the library page gets a Public / Private switch. Private files are uploaded straight to
  the private store, keep their own folders and have no address: the dashboard shows them through the API with the
  admin's session, and they can't be linked to, picked for a product or reached from the storefront. A file's
  details panel moves it between the halves, and making one private takes the public original and every resized
  copy of it down. Without a private store the library is what it was.
- **A private file can be shared with a customer.** From the file's details panel, with an optional download limit
  and last day. It shows under Downloads in the customer's account and is streamed through the same token link a
  digital purchase uses. Sharing again starts the share over under the new limits, a share can be taken back, and
  it ends when the customer's account is deleted or erased. Only private files are shared, and only with an open
  account. `myDownloads.productId` is now nullable on the storefront API, since no
  product stands behind a shared file.
- **The private half has permissions of its own.** `media.private.view`, `media.private.manage` and `media.share`
  sit on top of `media.view` and `media.manage`, so someone who looks after product pictures can't open, change
  or share a private file, and never sees the Private switch. They count only when granted globally, since the
  library isn't split by channel. Moving a file between the halves takes the grant for both, a share also takes
  `customers.view` on the customer's channel, and who a file is shared with is kept back from an admin who may
  not see that customer. A private picture is never sent to the AI provider for alt text.

- **Private files have a store of their own.** Set `PRIVATE_S3_BUCKET` (or `PRIVATE_STORAGE_DIR` on the
  filesystem driver) to a bucket with no public access, and exports, import uploads and the files shoppers send
  through forms are kept there instead of in the media bucket, where only a random address stood between them
  and anyone. At boot the app tries to read a file from that store without credentials and refuses to start in
  production if it can. The dev stack creates and uses a `private` bucket.
- **Files sent through a form can be downloaded in the dashboard.** The submissions page lists each
  submission's files, fetched through a route that checks the admin's grant to read that form's submissions.
  They were stored before, but there was no way to open one.

- **The role editor shows what a permission does.** Each permission's description sits under its name, so a grant
  that only counts on all channels, or one that moves money, says so where it is given.

### Changed

- **Downloads in the dashboard are saved by the browser.** Exports, import templates, form uploads and private library files used to be fetched into the
  page's memory before being saved, which strained the browser on large files. The dashboard now asks
  `/api/admin/download-ticket` for a link to the one file, good for a minute and tied to the admin's session, and
  the browser streams it to disk.
- **The admin file routes answer 401 when there is no session.** Export and import downloads, form uploads and library
  files used to answer 403 for an expired session as well as a missing permission, so the dashboard couldn't tell when to renew
  the session. It now renews it once and tries again, the way GraphQL requests do.

- **A blog post starts in a dialog.** "New post" on the posts list and on the CMS home asks for a title, with the
  slug following it, the language and an optional excerpt, then goes straight to writing. `/blog/posts/new` still
  works: it opens the list with the dialog up.
- **A post is written on a page.** The title and the body are typed where they will read, on a sheet set on a
  desk. A formatting bar floats above it with undo and redo, bold and italic, a style menu that names each style
  and shows it as it reads, lists, links, images and blocks. A capsule under the page counts the words, estimates
  the reading time (one click stages it as the post's reading time), names the language, says whether anything is
  unsaved and zooms the page.
- **A post's settings sit beside it.** Publishing, the slug and reading time, translations, the excerpt, categories
  and tags, search settings with a preview of the search result, and stores are sections of one panel, which closes
  to leave only the page. A store's noindex that was switched but not yet saved stays staged while the panel is
  closed.

- **A campaign is written as a sentence.** The new campaign page reads "Send *this email* to *these people*
  *now*", and each underlined part opens the control that sets it: the library's emails by name and subject,
  everyone, a customer group or a segment, and now or a set time. An A/B test adds a second sentence for the
  other subject, the share of the audience, how long the test runs and what decides the winner.
- **The page shows what a send will do before it goes.** The email as it lands in the inbox, with both subjects
  for an A/B test, above the opened email. How many of the audience are opted in, and how an A/B test deals
  them out. And when each part goes out. Send now or Schedule then asks once, repeating the sentence.
- A scheduled, sending, sent or cancelled campaign opens on the same sentence.
- **A draft remembers when it plans to go out.** The time picked in the sentence is saved with the draft
  (`scheduledFor` on `SaveCampaignInput`) and is there when the draft is opened again. Nothing is sent until the
  campaign is scheduled.
- **The share an A/B test may take comes from the server.** The admin API's new `campaignLimits` carries the
  bounds, so the slider and the save can't disagree.

- **The CMS home leads with everything you can open.** Pages come first, with how many there are, a mark for each
  one by state and the last edit. Page types, attributes, sections, block types, the blog, menus and forms follow,
  each with a small drawing, a count, an arrow to open it and a note saying whether it's for pages, the blog or
  the storefront.
- **Beneath it, a map of the site.** Every page is drawn as a card listing the blocks it's built from, top to
  bottom, with its state, address and last edit. Pages sit in lanes by where they live on the site, or by page
  type. The board narrows to a state or to a title or address you type, and picking a kind of block (content,
  media, catalog and blog) shows where it's used.
- **A page's content says which blocks it holds.** `outline` on the admin API's `CMSPageContent` lists the body's
  block types in order, with a container opened onto what it holds, so a list can show how pages are built
  without loading every body.
- **The admin API counts pages and posts.** The new `cmsPageCount(filter)` says how many pages a filter matches
  beyond what `cmsPages` hands over, and `blogPosts` now fills `totalCount`, which it declared but always left
  empty. The CMS home uses both, so it shows the real number of pages on a site larger than the board draws.

- **The flow builder has the email editor's layout.** Steps sit in a rail on the left, as icons on a narrow
  screen and labelled tiles on a wide one. The panel on the right has a Step tab for the selected step and a
  Flow tab for the name, what starts the flow, its status and its checks, with undo, Save and Activate pinned
  below it. Zoom, tidy up, the step count and the checks sit above the canvas.
- **A dot on a step leads one way.** Connecting a dot that already led somewhere moves the connection, since a
  flow only ever follows the first.
- **The transactional switch follows the trigger.** It turns on with an order or account trigger and off with
  any other, where it can no longer be switched on only for the save to be refused.
- **`flowTriggers` replaces `flowTriggerTypes` in the admin API.** Each trigger now comes with whether its flows
  may be transactional and whether they carry a one-time link, so the builder asks instead of keeping its own
  copy of those lists.

- **The media library is a wall of its pictures.** Files hang in rows at their own proportions instead of square
  crops, with a size slider and a list view beside it. The library's top level shows everything, newest first,
  and a folder shows what is in it and in the folders under it.
- **Files come in by drop, paste or the button, several at once.** Each shows its progress, and the last one in
  opens ready for its alt text. The one-file upload dialog is gone.
- **A picked file opens beside the wall.** Its picture, focal point, alt text, title, caption and notes, then its
  file name and folder, with rename, move and delete. Picking another file while words are unsaved asks first.
- **Several files can be picked** with Ctrl or Shift and moved to a folder or deleted together. A failure says
  how many didn't go through and leaves those picked.
- **Filters and folders.** Everything, images and documents each show their count, the sort order is kept
  between visits, the folders inside the open one are a click away above the wall, and folders are made and
  renamed in a dialog.
- **The wall and the picker show small copies of pictures**, not the files themselves, so a page of large photos
  loads in kilobytes. A picture whose copy can't be made shows its original. In the dark, transparent pictures
  sit on a light checkerboard, so a black logo stays visible.
- **The file dialog offers what the server takes**, video included, instead of a list kept by hand.

- **`download.accessed` says which kind of file was downloaded.** Its payload has a new `AssetID`, set for a file
  the shop shared from the media library, and `ProductID` is null for those instead of an all-zero id. A file a
  customer bought looks the same as before.
- **A shared file's title stays out of webhooks.** `download.accessed` for a file shared from the media library
  carries an empty `Title`, since it's the shop's own name for a private file.

- **Production needs a private store to start.** `PRIVATE_S3_BUCKET` (or `PRIVATE_STORAGE_DIR` on the filesystem
  driver) is required when `APP_ENV=production`. Without one, exports, import uploads and form uploads would sit in the public
  media bucket behind a random address. Add a second bucket with no public access before upgrading.

### Fixed

- **What one admin fetched is let go when they sign out.** The dashboard's cache kept everything the admin before
  could see, so the next admin to sign in on the same tab was first shown it. Signing out now empties the cache, and
  someone else signing in - in this tab or another - reloads the page.

- **Saving a draft campaign keeps its own email.** A campaign that carried its own content instead of a library
  email lost it on the next save.
- **A/B results show on the campaign.** A campaign with a subject test lists both subjects' sends, opens and
  clicks, and the winner, once it's scheduled or sent. The table existed, but no page reached it.
- **Saving or scheduling a new campaign no longer asks whether to discard unsaved changes.** The page moved to the
  campaign's own address right after the save, and the leave-page prompt took that for walking away from it.
- **A campaign page says when something failed.** A preview that didn't render, an audience that couldn't be
  counted and a send that couldn't be cancelled each show the reason instead of waiting forever or saying nothing.

- **The delete key no longer removes a flow's trigger.** A flow can't be activated without one, and there was no
  way to add it back.
- **A flow can't be activated with a placeholder email.** A send-email step with no email picked would send the
  "Hello" placeholder it was created with. A new step now starts empty.
- **A flow that can't run can't be activated, whoever asks.** The server refuses a flow with nothing after its
  trigger, a loop, or a step on the way that's missing its email, message, segment or URL. The builder already
  held the button back, but a direct API call went through.
- **The flow builder says when its lists didn't load.** A failed load of the triggers, segments or emails shows
  under the Flow tab instead of leaving empty menus.

- **Removing a storefront no longer leaves the dashboard's previews on its port.** `skelet add channel` points
  the previews at the project's first storefront (`VITE_STOREFRONT_ORIGIN` in `.env`), and `skelet rm channel`
  left that behind, so the CMS and blog previews showed "localhost refused to connect". They now move to the
  next storefront of the project's own, or back to the default. A value set by hand is left alone.

- **SVG uploads work when the admin API has a slug.** The dashboard posted them to `/api/admin/<slug>/media/svg`,
  a path the backend never served, so with `ADMIN_API_SLUG` set every SVG upload failed with a 404.

### Security

- **Go 1.27.4.** Fixes a vulnerability in `net/http` (GO-2026-6859), which every HTTP path in core reaches.
